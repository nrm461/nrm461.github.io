## How to deploy (critical)
**PRIMARY — direct `git push` from the cloud container (set up 2026-07-18, fast).** `github.com` HTTPS git is reachable for BOTH fetch and push; only the placeholder token was the old blocker. Recipe: clone the repo, `device_stage_files` the token from the connected website folder (`token/git-token`), then push with an inline credential helper (token never printed). One commit for many files, no browser, no per-file `sha` dance, no 90s wait unless you want to watch the Action. Full recipe: project memory `deploy.md`.

FALLBACK — **GitHub Contents API from a browser tab** on an `nrm461.github.io` origin (token in `localStorage.ghtoken`, set by `/admin/`): fetch file → mutate in-browser → PUT with its `sha`. Use only if the token can't be staged (desktop not connected). `api.github.com` is still proxy-blocked from the container, so the browser remains the fallback channel.

Either way: commit ONLY source; the Action rebuilds HTML. Large/binary assets (deck frames, multi-MB data JSON) push fine now via git — no longer need Nick's local clone.

- Site pages are GENERATED by `_build/build_site.py` — never edit generated HTML; edit the data/generator and let the build Action regenerate. Commit ONLY source (`data/`, `css/`, `js/`, `_build/`); the Action rebuilds HTML on push and skips messages containing `[auto-build]`.
- `/deck/` is generated by `_build/build_deck.py` (reuses build_site's shell). Note: `claude_project/` and `deck/` are NOT Action trigger paths, so committing docs is harmless.
